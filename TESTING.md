# Testing Horse & Rider's Companion

The supported test toolchain is pinned in [.fvmrc](.fvmrc): **Flutter 3.47.9**
with **Dart 3.13.7**. The live app manifest requires Dart 3.12+ / Flutter 3.44+.
CI and the project editor settings use the same selected Flutter release.
Also install Python 3 and Node.js 20.19+ with npm; deployed functions target
Node 20 according to their package manifest.

## Run the checks

From the repository root:

```sh
python3 tool/check.py
```

This resolves Flutter dependencies, analyzes app/test/package code, tests the
coverage-report calculation, runs every Flutter test with package coverage,
then lints and tests the Firebase functions. It returns a nonzero exit code if
any check fails and continues independent checks so failures remain visible.
Informational Dart style lints are reported; errors and warnings fail analysis.

The runner uses `FLUTTER_BIN`, the SDK configured in VS Code if available, or
Flutter on PATH. It verifies the version against the project pin. It also pins
child-process SDK paths and rejects dependency metadata generated by another
SDK. If that happens, close competing dependency-resolution commands and rerun
without `--no-pub`.

Options:

- `--no-pub`: reuse dependency metadata that already matches the selected SDK.
- `--skip-functions`: run Flutter and coverage-tool checks without Node/npm.
- `FLUTTER_BIN`: select a Flutter executable explicitly.
- `NPM_BIN`: select npm explicitly; its Node executable must also be on PATH.

VS Code tasks provide **Check app and backend**, **Check Flutter only**, and
**Build web for validation**. To compile the production JavaScript web app:

```sh
flutter build web --release --no-pub
```

## Focused checks

```sh
flutter test test/routes_flow_test.dart test/app_authorization_test.dart
flutter test test/cubits
flutter test test/domain
flutter test test/widget
npm --prefix functions ci --ignore-scripts
npm --prefix functions run lint
npm --prefix functions test
python3 -m unittest discover -s test_tools
```

All Dart tests are under [test/](test/), including tests of the four local
packages. Running tests only from inside a package will miss those tests.
The shared offline fixture is [app_test_harness.dart](test/support/app_test_harness.dart).

## Firebase sign-in and catalogue reads

- The app subscribes once to Firebase `userChanges()` through
  `AuthenticationRepository`. Email/password and Google sign-in feed the
  same app session. Native Google Sign-In initializes in bootstrap with the
  app's OAuth configuration. Web uses the Firebase popup. Login forms allow
  one submission at a time, trim email input, and ignore completions after
  their cubit closes. Firebase's invalid-credential response becomes a
  clear email or password error.
- Registration updates the Firebase display name and sends a verification
  email. While verification is pending, the account has guest access and the
  app reloads the Firebase user every 10 seconds, with one reload in flight.
  The prompt opens once per pending email while the navigation shell is
  mounted. A verified user update closes it and starts one live
  rider-profile document listener. Repeated user events and name or photo
  changes reuse the listener. The profile snapshot determines whether the
  profile is set up. Notification registration is requested on the first
  existing profile snapshot for that session.
- Firebase sign-out and account switches discard account state and cancel its
  profile, horse and messaging listeners. Explicit sign-out waits for Firebase
  to succeed before changing the UI. Public catalogue data stays available.
  Guest browsing uses signed-out access and does not create anonymous Firebase
  users. The deployed Firestore rules must allow the public catalogue queries.
- Resource links are stored as an array of skill IDs in `skillTreeIds`. Before
  the full Resources snapshot arrives, a skill detail uses one live
  `array-contains` query for its skill ID. When the full snapshot is available,
  the detail filters it in memory and releases the scoped listener. An empty
  full snapshot also counts as loaded. Multi-skill resources appear under each
  linked skill. A failed full listener is canceled so a later load can retry.
- The conversations query starts once for the current rider, including while
  the first snapshot is pending.

| Remaining full or unbounded Firestore reads | When the app uses them |
| --- | --- |
| Skills collection | One live catalogue at startup for the profile and Skill Tree, including local search and filtering. |
| Resources collection | One live catalogue after opening the Resources branch or using the resource picker from a skill. Resource comments and web views are nested under that branch. The catalogue supplies local search, sorting, and live comment updates. |
| Messages subcollection for a conversation | One conversation's complete message history when it is opened. The parent conversations query is filtered by rider. |

Training paths are disabled and their full-collection query is dormant.
The ordered-resource and published-article query methods have no live callers.
The query-count tests count repository calls, which represent app listener
creation. Firestore can reconnect or serve snapshots from cache independently.

## Coverage reports

Each complete check run regenerates:

- `coverage/lcov.info`: executable-line coverage for the app and local packages.
- `coverage/summary.md`: component totals, largest gaps, and source files absent from LCOV.
- `coverage/summary.json`: the same measurements for scripts.
- `coverage/run_status.json`: SDK and test-run status.

Duplicate LCOV records are merged by line. External SDK files are excluded.
Failed test runs are explicitly marked as incomplete, and stale summaries are
removed before testing. Files absent from LCOV are excluded from the percentage
and listed separately. Archived implementation tests contribute to measured
coverage. A passing suite or line-coverage percentage does not establish that
every feature works end to end.

## Remaining integration work

These tests use mocks or fake Firestore and never require production credentials.
They do not verify deployed Firestore rules/indexes, real OAuth and email
verification, file picking and Storage uploads, native plugin registration,
push delivery, ads, or device behavior. Backend tests also replace CORS and
Firebase trigger registration.

Profile-search stream/error behavior, edit-profile forms, file uploads and much
of AppCubit remain significant coverage gaps. Before release, run real two-user
flows against an isolated emulator/staging project, then smoke-test web and
Android/iOS devices. Validate ownership transfer acceptance and server-enforced
permissions, not just UI controls. The backend's email notification function
currently logs a stub message rather than sending email.

**Horse-transfer acceptance is not implemented.** Request creation is tested,
but acceptance currently returns a clear error and leaves ownership unchanged.
That test documents the limitation; it does not demonstrate a working ownership
transfer. Skill-tree edit requests also have a placeholder acceptance handler.

The standard JavaScript web build is checked. A WebAssembly dry-run warning from
`flutter_keyboard_visibility_web` does not mean WASM support has been validated.

## CI

[test.yml](.github/workflows/test.yml) runs the full command, uploads coverage,
and compiles the production web app. Hosting workflows run Flutter tests before
their build/deploy steps. Updating workflows does not deploy the app locally.
